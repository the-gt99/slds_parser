# Переход на Rules v2

## Состояние

В production выбран режим v2; изменения старого каталога заморожены. API и worker
используют `RulesExecution` с неизменным снимком `RulesV2Runtime` на одну операцию.
В текущей локальной ветке processing в режиме v2 использует прямой selector, записывает состояния и
ревизию в `internal_products.data.rulesV2` и не пишет старые observations.
Существующие observations остаются в БД для отката и исторического аудита;
страница товара с сохранённым `rulesV2` показывает новые решения. Старый
`ProductClassifier` остаётся для режима v1 и отдельных проверок совместимости.
Переключение режима не означает, что старые таблицы и код можно удалить.

Подготовлен отдельный прямой исполнитель `DirectRulesV2Assignments`: он выбирает
победившее source-правило, назначает WordPress terms и переводит условия
`resolved.*` в проверку уже назначенных term ID. Прямой путь передаётся в
обычные WordPress preview/export через `RulesExecution.resolveDirectTarget` в
режиме v2; в режиме v1 resolver возвращает `null`. Основные mappings,
проекции и дополнительные назначения теперь используют прямой результат.
Дополнительный бренд по заголовку получает явный признак подтверждённого
source-brand. Сохранённый DTO товаров, ещё не прошедших повторную обработку v2,
может содержать старую классификацию. Перед WordPress preview/export в режиме
v2 она удаляется из подготовленного DTO: payload больше не вызывает старый
классификатор. Прямой исполнитель читает
`referenceCandidates` из сохранённого DTO, чтобы сохранить контекст точных
сопоставлений, но при исполнении не обращается к старым mapping-таблицам.

Исполнитель сохраняет полные ключи точных сопоставлений (источник, тип, scope,
нормализованное значение, полный contextKey), ignored-решения, исходные ID и
ревизии. Классификационные условия выполняются существующим проверенным
алгоритмом. Проекции применяются к победившему решению, а не просто к совпавшим
условиям. Новые назначения поддерживают AND между группами, OR внутри группы,
несколько действий и общий DTO через `common.*`.

Точные условия новых назначений индексируются по одной необходимой AND-группе,
с включением всех её OR-веток. Правила без пригодного точного условия проверяются
отдельно. Тест содержит каталог из 50 000 точных правил.

## Несовпадения контрактов, проверенные 20 сентября 2026

Read-only запросы к production выявили:

- `context.family`: 10 063 активных классификационных правила; поле `family`
  присутствует в контексте 20 692 точных сопоставлений.
- `context.brand`: 10 063 правила; контекст 20 979 точных сопоставлений.
- Дополнительные поля контекста точных сопоставлений: `productCategory` (77),
  `productType` (77), `audience` (73), `route` (69), `ageGroups` (13).
- Назначения используют результаты предыдущей классификации: `resolved.model`,
  `resolved.brand`, `resolved.tag`, а также отсутствие `resolved.activity`.
- 23 условия каждого вида проверяют `product.metadata.source` и
  `product.metadata.productId` вместе с точным названием товара.

Это исторические измерения, не оперативные счётчики. Перед переключением
нужна повторная проверка.

CommonProductDTO v1.1 содержит `characteristics.family` и `characteristics.ageGroups`.
`productType` отдельно не добавлен: `characteristics.category` уже содержит
структурный тип (для GOAT: productType → productCategory → route).
Исходные productType/productCategory/route и дерево категорий сохраняются отдельно
и доступны по существующим путям `product.attribute.*` / `product.metadata.route`.
Эти пути читают сохранённый processing DTO, а не произвольный raw payload донора.
Промежуточные resolved-значения в общий DTO не добавлены. Нельзя заменять контекстные условия
условиями только по названию или бренду. До согласования контракта мигрированные
правила сохраняют исходную семантику в слое совместимости. Новые характеристики
заполняются только из сохранённых фактов; family не выводится из названия,
ageGroups не выводится из пола или размера. Отсутствующие данные — null / [].

## Проверка без записи

`RULES_V2_AUDIT_LIMIT` задаёт число товаров (по умолчанию 1000),
`RULES_V2_AUDIT_AFTER` — ID, после которого продолжается выборка.
Команда использует repeatable-read read-only транзакцию и сравнивает:

1. классификацию и observations;
2. основные target mappings;
3. дополнительные проекции;
4. назначения, включая ошибки конфликтов.

Код завершения ненулевой при расхождениях или пустой выборке. Новые v2-правила
могут давать ожидаемые различия, но их нельзя автоматически объявлять безопасными.
Проверка не заменяет сравнение полного WordPress payload/preflight. Совпадение
на выборке не является доказательством совпадения на всём каталоге.

`RULES_V2_PAYLOAD_IDS=... npm run rules-v2:audit-payload` принимает от 1 до 20
явных ID. Команда сравнивает полный payload обоих контуров, включая ошибки,
и при совпадении вызывает существующий read-only WordPress preflight.
Ошибки идентичности не обходятся и приводят к ненулевому коду завершения.
Команда не сохраняет снимки, не включает target и не вызывает upsert/export.

Для проверки прямого пути используются `rules-v2:audit-direct-plan`,
`rules-v2:audit-direct-matches`, `rules-v2:audit-dependencies` и
`rules-v2:audit-direct-assignments`. Последняя команда читает товары страницами
по 200 без долгой транзакции; `RULES_V2_DIRECT_ASSIGNMENT_AFTER` позволяет
продолжить с сохранённого ID. Совпадение отдельных сегментов нельзя выдавать
за завершённую сверку всего каталога. `rules-v2:audit-payload` дополнительно
сравнивает прямой WordPress payload, собранный без сохранённой классификации,
с текущим v2 payload и выполняет только read-only preflight.
Снимки правил и старой базы решений загружаются в короткой read-only транзакции;
она завершается до чтения товаров и сетевых WordPress preflight. Команда
отклоняет результат, если ревизия правил или target-справочника изменилась
во время проверки.

21 сентября полная длительная сверка назначений остановилась после 26 тысяч
товаров с нулём расхождений: PostgreSQL повторно перешёл в recovery после
аварийного завершения backend-процесса с кодом 2. Последующая проверка payload
на 20 товарах также прервалась при новом recovery; её нельзя считать пройденной.
Причина не подтверждена; не запускать снова нагрузочный production-прогон до
диагностики стабильности БД.

Проверка системных журналов 21 сентября выявила повторяющуюся ошибку
`invalid page in block 23650 of relation base/16384/69677` уже 18 сентября
при `UPDATE source_products`, до остановленного аудита v2.
В журнале контейнера также видны три завершения backend с кодом 2
20–21 сентября и последующий recovery. Дополнительный recovery около 00:38 UTC
21 сентября произошёл рядом с короткими диагностическими подключениями.
Связь конкретного повреждённого блока
с этими завершениями пока не доказана; текущая relation по прежнему filenode
не определяется. Нужна диагностика целостности БД и хранилища на стороне
PostgreSQL до возобновления массовых проверок. Повторение того же аудита
меньшими страницами само по себе не устраняет риск.
До проверки отдельной копии не выполнять даже точечные диагностические SQL
на production: короткие запросы не доказали безопасность сервера.

## Реализовано в редакторе и импорте

- Несколько групп И с условиями ИЛИ, несколько действий, сохранение всех условий
  при повторном открытии. Запятые внутри регулярных выражений сохраняются.
- Поиск, страницы по 100 записей и три счётчика формы условий. Счётчик точных
  условий означает одно `equals`, а не доказанную независимость от старых решений.
- Редактирование импортированных копий с optimistic revision и аудитом.
  Ручные копии помечаются `manualOverride` и больше не перезаписываются импортом.
- Точная зависимость проекции сохраняется: можно изменить назначаемое значение,
  но нельзя превратить зависимость от победившего решения в произвольное условие.
- Импорт выключает копии удалённых исходных записей, не удаляя историю.
- Native preview использует один repeatable-read снимок, прямой V2 resolver
  без старого классификатора и последние 200 товаров донора. Нулевой охват
  такой выборки не означает отсутствие совпадений во всём каталоге.
- Неизвестные пути общего DTO отклоняются, а не считаются пустым полем для `absent`.

Реальная SQL-проверка `tests/integration/rules-v2-sql-smoke.ts` выполняется только
при `RULES_V2_TEMP_SQL_SMOKE=1`. Она создаёт TEMP-копии трёх writable-таблиц,
с собственными последовательностями, проверяет создание, редактирование,
конкурентную ревизию и повторный импорт. Общие справочники читаются без записи.

## До удаления старого контура

- Разобраться с повторным аварийным завершением backend PostgreSQL и безопасно
  закончить полную сверку прямых назначений. Сравнить полный WordPress payload
  и ошибки на репрезентативной выборке, затем на всём каталоге без опасной
  долгой production-транзакции.
- Проверить прямые processing/reclassification и хранение `rulesV2` на локальной
  PostgreSQL и ограниченном production smoke после восстановления стабильности БД.
  До этого не считать новый путь эксплуатационно подтверждённым.
- Проверить подключённый прямой путь в реальных preview/export: readiness,
  size conversion, primary brand, content templates и полный taxonomy diff.
- Перевести редактор импортированных source-правил и страницы товаров с
  административный API с чтения старых `reference_values` и observations на
  собственные данные v2; проверить все оставшиеся SQL-зависимости.
- Выполнить ограниченный сквозной smoke после сборки, миграций и перезапуска,
  не включая WordPress target и не запуская массовый export. Только после
  подтверждённой парности и отката удалять старые таблицы и код.

Старые таблицы и значения до этого не удалять. Переключение правил не разрешает
включение target или массовый экспорт в WordPress.
