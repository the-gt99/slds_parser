# Вторая копия изображений

Основное хранилище и публичные URL остаются прежними. При полной настройке
`PARSER_S3_MIRROR_ENDPOINT`, `PARSER_S3_MIRROR_REGION`, `PARSER_S3_MIRROR_BUCKET`,
`PARSER_S3_MIRROR_ACCESS_KEY_ID`, `PARSER_S3_MIRROR_SECRET_ACCESS_KEY` публикация
сохраняет намерение второй копии в PostgreSQL до загрузки в основное S3.
Частичная конфигурация запрещена. Секреты задаются вне репозитория.

Pipeline worker обслуживает отдельную последовательную lane `mirror_image`.
Он читает подтверждённое содержимое из основного S3, сверяет SHA-256 и размер,
переносит Content-Type, Cache-Control и metadata с исходным ключом.
Условный PUT `If-None-Match: *` запрещает перезапись отличающегося объекта.
Для существующего объекта проверяются размер, заголовки и ETag; только при
непригодном для сравнения multipart ETag требуется чтение второй копии.
Передача использует Content-MD5 и штатные проверки SDK.

Это гарантированное отложенное копирование, а не синхронная запись в два S3.
Локальный файл удаляется после успешной основной загрузки: задача уже сохранена,
а источником её повторения служит основной S3. Ошибка сохранения задачи оставляет
локальный файл. Основное S3 нельзя удалять, пока есть незавершённые копии.

Служебный `transfer-legacy-images` использует ту же очередь, сохраняя исходные
legacy-ключи. Его прежние проверки содержимого S3, CDN и неизменности локального
файла остаются обязательными перед удалением. Включение зеркала само по себе
не запускает эту административную службу.

Временные сетевые ошибки, 404 ожидаемого первичного объекта, 409, 429 и 5xx
повторяются до 12 попыток, с задержкой от минуты до часа. Конфликт содержимого,
метаданных, ошибка доступа или неверная конфигурация требуют исправления причины.
Failed mirror jobs не удаляются обычной очисткой истории. Их можно отфильтровать
на странице задач как «Вторая копия фото». Для повтора используются административные
`POST /api/jobs/failed/preview-retry` и `POST /api/jobs/failed/retry` с
`jobType: "mirror_image"` и явным `limit`. Требуется обычная авторизация администратора;
сначала проверяется preview. Повторная публикация не создаёт дополнительные задачи.
Таблица `image_mirror_objects` сохраняет квитанции независимо от очистки completed jobs.

Контроль очереди:

```sql
SELECT status, count(*), min(created_at) AS oldest
FROM jobs WHERE job_type = 'mirror_image' GROUP BY status;
SELECT count(*), min(created_at) AS oldest
FROM image_mirror_objects WHERE copied_at IS NULL;
```

До включения настройки применить миграцию 111. После включения проверить
ограниченную публикацию, наличие обоих объектов, равенство содержимого и metadata,
повторное исполнение без PUT и отсутствие новых задач при повторной публикации.
При отключении настройки очередь перестанет исполняться; её строки необходимо
сохранить до возобновления или явно согласованного завершения переноса.

## Production после переноса

Публичный адрес API: `https://parser.slamdunk.shop`, сервер `186.246.44.157`.
Конфигурация Nginx: `deploy/nginx/parser.slamdunk.shop.conf`. Сертификат выпускается
для этого домена через ACME; файл `/etc/nginx/parser-maintenance.flag` временно
закрывает API кодом 503, сохраняя отдачу изображений.

Рабочие службы: API, pipeline worker, отдельные inventory workers GOAT, Shihuo
и WordPress, content worker. Сохранены таймеры очистки и GOAT discovery.
Общий inventory worker и административный перенос старых изображений не должны
запускаться одновременно с этими специализированными службами без отдельной задачи.
Настройки потоков берутся из перенесённых runtime settings и systemd overrides.

Шлюз Shihuo на сервере сайта использует `https://parser.slamdunk.shop` как API base.
После изменения этого адреса требуется перезапуск mitmproxy: конфигурация читается
при загрузке модуля. Адрес локальной проверки сертификата шлюза не является адресом
парсера и при переносе не меняется.

Предыдущий сервер Jino сохраняет базу, файлы и конфигурацию финального снимка.
Его API, workers и два таймера остановлены; Nginx пересылает старые API-ссылки
на действующий публичный адрес. Яндекс остаётся основным хранилищем.

После появления записей на новом сервере откат требует сначала остановить все
его writers и таймер шлюза, затем перенести обратно актуальную полную базу,
состояние файлов, код и конфигурацию второй копии. Только после сверки можно
восстановить прежний Nginx, маршрутизацию и запустить старые службы.
Запуск замороженной старой базы потеряет изменения, сделанные после переключения.
