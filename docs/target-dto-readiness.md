# Результирующий DTO и готовность товара

## Основной контракт

Оперативная модель конвейера:

`данные донора → исходный UniversalProductDTO → правила V2 → результирующий target DTO → readiness → экспорт`

Готовность определяется только по результирующему DTO после применения всех
подходящих правил. Наличие или отсутствие отдельного старого classification
mapping не является самостоятельным критерием готовности.

Правила могут последовательно добавлять значения в одно поле. Совместимые
действия `add` объединяются с удалением дублей. Несовместимые `replace`, равные
приоритеты внутри одной конфликтной группы и взаимоисключающие изменения должны
останавливать readiness как конфликт. Для каждого итогового значения сохраняется
трассировка применённых правил.

## Минимальные требования

Для выгрузки товара обязательны:

- одно непустое название;
- одно непустое итоговое описание;
- хотя бы одно изображение;
- хотя бы одна вариация;
- хотя бы один `pa_brand`;
- хотя бы один `pa_model`;
- хотя бы один `product_cat`;
- у каждой вариации один исходный размер и одно состояние наличия;
- у каждой доступной вариации одна цена.

`pa_brand`, `pa_model` и `product_cat` множественные. Их значения могут добавлять
разные правила. Для readiness у них нет обязательного единственного основного
значения. Выбор бренда для конвертации размерной сетки является отдельным
техническим решением exporter-а и не меняет множественность `pa_brand`.

Необязательные поля:

- `pa_tsvet` и подробная source-расцветка — разные данные;
- `pa_material` — множественное;
- `pa_vid` — множественное;
- `pa_shoe_height` — единичное;
- `pa_season` — единичное;
- `product_tag` — множественное обогащение из брендов, моделей и других правил;
- дата релиза — необязательный факт для контента и дополнительных данных.

Audience и family не являются самостоятельными обязательными WordPress-полями.
Audience используется как факт для категорий и размерной сетки, family — как
контекст правил модели.

## Причины незавершённости

Интерфейс должен различать:

- обязательного значения нет, хотя данные донора присутствуют: не хватает
  подходящего правила;
- обязательного значения нет и донор не дал подходящих данных;
- правило сработало, но не сформировало активное target-значение;
- несколько правил дали несовместимые изменения;
- товар нарушает структурный контракт: пустые название, описание, изображения,
  вариации, размеры или цена доступной вариации.

Рабочий экран `/rules-v2` показывает результат исполнения правил, причины
неготовности и трассировку. Поиск по названию, SKU, исходным признакам донора,
фильтры и сортировка выполняются по всему индексу готовности, а не в пределах
загруженной страницы. Пока индекс перестраивается после изменения правил или DTO,
экран показывает прогресс и не выдаёт частичные числа за полный каталог.

Создание правила из товара начинает с точного условия по
`common.source.productId`; оператор может заменить его более общим условием.
Перед сохранением нового прямого правила полная фоновая проверка показывает
охват всего обработанного каталога, заполненные поля, переходы в готовое
состояние, примеры до/после и конфликты. Изменение условия или действия после
проверки требует повторить её.

Текущий workbench выполняет прямые V2-назначения и минимальную структурную
проверку локально в read-only транзакции. Он не заменяет полный WordPress preview:
точные size mappings, перевод, content templates, сохранение существующего
описания и удалённый preflight по-прежнему проверяются общим exporter-ом. При
дальнейшем завершении перехода workbench должен получать тот же материализованный
target DTO, который передаётся exporter-у, без второго варианта правил.
